Case study · Famous People

A party game, an admin console, and 54 deploys — mostly from a phone.

What started out as a dream and idea 15+ years ago, made a reality today using Claude AI. Over four weeks I shipped a real multiplayer game, a private management dashboard, marketing site and case study, working with Claude. Here's the actual process, and the actual numbers.

9 August 2026· 10 minute read· Braden Turner, Pivot Dev Shop

Famous People is a name-guessing party game. Everyone joins from their own phone with a four-digit code, and the game passes between phones instead of the phone passing between people.

Behind it sits more than the game: a private admin dashboard for curating the deck, a marketing site, a database with security rules, and pipelines that put changes live. That's the surface area a small product team would normally carry. It was built by one person working with Claude, in evenings and gaps — and most of the driving happened on an iPhone. Not typing code on a phone. Describing what should change, reading back what Claude proposed, and approving it.

What got built

Three live surfaces, two codebases

The game

Play from your own phone

An installable web app. Host starts a game, players scan a QR code, everyone builds a secret list of names, then three rounds run across the group. Whichever phone is live drives the round — so the game survives the host's battery dying.

app.playfamouspeople.com
The admin console

Curate the deck

Approving names players submit mid-game, writing descriptions, organising categories, bulk edits. The difference between a demo and something you can actually run.

Private · not indexed
The marketing site

Explain it, collect signups

Explains the game and takes waitlist signups. Those signups write into the same database the game uses, so there's no third system to keep in sync.

playfamouspeople.com

React and Vite for the game, plain HTML for the dashboard, Firebase for the database and hosting, GitHub for the code and the pipelines. Roughly 18,000 lines across the two codebases.

Where it started

The whole game, in pencil

Before any code, every screen existed as an idea, a vision of the expereince, captured on these iPhone frames, 15+ years ago. Luckily I'd saved them and the inspiration came alive again with the introduction of Claude AI - Claude Design and Claude Code.

What's striking looking back isn't how rough these are — it's how little the structure changed. The screens that shipped are the screens that were drawn, because the cheapest thing in the world to argue with is a drawing. The photo-of-the-winners note is the exception that makes the point: finding out it wasn't worth building cost one pencil stroke.

Everything that did change came from watching people play. Hiding names someone else already took. Making the current player tap a card before their turn starts, so nobody's turn begins while they're still looking at their phone. Removing a Skip button that turned out to be a way to cheat. None of that is visible in a sketch — you only find it in a living room, which is what a forty-second release loop is really for.

Where it ended up

And here's what shipped

The same eight screens, in the same order, running on a phone. Put them next to the drawings and the thing worth noticing is how rarely anything moved.

Turning a sketch into a real life application validated ideas. In the sketch, three names written into three boxes and "I need inspiration" was the escape hatch for when a player got stuck. What shipped is the other way round: browsing categories is the main road, and typing your own is the field at the bottom. Nobody decided that in a meeting — it's what happened once real people met a blank text box and stalled.

Two screens here were never drawn at all. Hosting, above — the sketch imagined joining but not the person being joined. And a "who's playing" step that exists for one reason: at a real game night, somebody always turns up without a phone, and the host has to be able to add them.

Eight lines added, four removed, one file. Reviewing took ten seconds because there were ten seconds' worth of it to read. The point isn't that the code got written fast — it's that nothing sat in a queue. No ticket waiting for a sprint, no reviewer to find, no release train to catch.

It's also a fair illustration of the limits. Nobody validated that the new spacing is right; I looked at it and thought it was better. A ten-second review is honest about small, visual, easily-reversed changes and dishonest about anything else. The discipline isn't reviewing faster — it's keeping changes small enough that a fast review is a real one.

Where and when

Built in the cracks, from a phone

In the game's codebase, only 3 of the 107 commits were typed directly on a laptop — all three in the first two weeks, before the pipelines existed. What makes phone-driven work possible isn't a clever editor. It's that running the code, reviewing it and releasing it all became things a machine does on its own. What's left is judgement, and judgement fits on a phone.

The toolkit

What's involved, in plain terms

The builder

Claude Code, mostly on iPhone

I describe a change in a sentence; Claude reads the whole project, makes it, and opens it for review. The laptop was for setting up and the occasional change needing a lot on screen at once.

The design step

Sketches, then Claude prototypes

Pencil first, then clickable prototypes built in Claude. Far cheaper to throw away than a built feature — and the colours and spacing from those prototypes became the app's real design system.

The memory

A project notes file

Each codebase carries a written file of hard-won knowledge — the traps, the conventions, what broke before. Claude reads it every session, so a lesson learned once isn't re-learned. The highest-leverage file in the project.

The workflow

GitHub

Holds every change as a reviewable proposal with its own explanation. Nothing goes live without passing through one, so there's a written record of every decision — including the wrong ones.

The safety net

Automated pipelines

On approval: check, build, publish, report which version went live. They also run database migrations, so data changes happen somewhere logged and repeatable rather than on a laptop.

The infrastructure

Firebase

The live database that lets four phones see one game, plus hosting for all three sites. Security rules are deployed by hand on purpose — a bad one takes everything down at once.

What actually made it fast

Four things that mattered more than typing speed

Automate releasing before you build features

For 18 days I deployed by hand and averaged just over one change a day. The day that became automatic, the average went to 18 a day and stayed there. Nothing about the assistant changed; the friction between "done" and "live" did.

Write down what you learn the hard way

Every trap this project hit is a line in a notes file the assistant reads first. Without it you re-explain your product every session — and it makes the same mistake twice.

One decision per change

Nearly all 77 changes did a single describable thing. Small changes are reviewable on a phone in a minute. Big ones aren't reviewable anywhere, which is how bad code slips through.

Let the machines hold the line

A release once went perfectly green while shipping an app that couldn't reach its database. The fix wasn't to be more careful — it was to make the build refuse to produce that outcome. Rules a machine enforces beat intentions a person holds.

The honest part

Four things that went wrong

Any case study showing only good numbers is selling something. Each of these cost an evening.

A perfect release that shipped a dead app

The app's settings are baked in at build time. The first time building moved off my laptop the pipeline couldn't see them, so it built an app pointed at nothing. Every screen said it couldn't reach the game server. The release reported success in bright green.

Fixed by making the build fail loudly rather than produce a broken app quietly.

"The fix didn't work" — except it did

Apps installed on a phone cache themselves, so a phone can keep running yesterday's version after a perfect release. I burned real time chasing bugs that were already fixed.

Now the first thing to check, written down.

A migration that crashed and reported success

A script updating every record crashed on its first line — and the run went green anyway, because of how the command was written. It reported changes it never made. Worse than failing.

One line of configuration made failures actually fail.

Players' names quietly vanishing

Two pieces of code both added players to a game and the wrong one silently won. Names appeared in the lobby, then didn't. Exactly the duplication that creeps in when you build quickly.

Both paths now go through the same code.

Notice the pattern. None of these were the assistant writing bad code. Three of the four were systems reporting success while failing — the exact failure mode you get when you ship fast and trust green ticks. Speed doesn't remove the need for judgement about what "working" means. It raises the price of not having it.

If you manage products

Why this is worth your afternoon

A prototype can now be the real thing

The gap between a clickable mock and software people can use has narrowed enormously. That changes what's worth arguing about in a room: you can often settle it by building the thing in an evening and watching six people use it.

Specification is the skill that matters

Every good change started with a clear, small description of a problem. Every bad one started with a vague ask. Writing precise requirements and spotting when something is nearly right is a product manager's job already.

The bottleneck moves, it doesn't disappear

With building this cheap, the constraint became knowing what to build and being honest about whether it worked. Those were always the hard parts — this just removes everything that used to hide them.
